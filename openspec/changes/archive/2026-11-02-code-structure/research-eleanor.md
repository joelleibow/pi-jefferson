## The host: how it discovers and executes extensions (evidence)

Host source: `node_modules/@earendil-works/pi-coding-agent/dist/core/extensions/loader.js`,
`dist/core/package-manager.js`, `dist/core/pi-manifest.js`; docs: `docs/packages.md`,
`docs/extensions.md`.

### 1. Discovery of an entry point

**Local discovery dirs** — `discoverExtensionsInDir` (loader.js:635), called for
`<cwd>/.pi/extensions/` and `<agentDir>/extensions/` (`~/.pi/agent/extensions/`):

1. Every **direct** `.ts`/`.js` file in the directory is loaded as an extension.
2. A subdirectory is resolved only via `resolveExtensionEntries` (loader.js:596):
   its `package.json` `pi.extensions` array, else its `index.ts`/`index.js`.
3. **No recursion beyond one level.**

**Installed packages** — `pi install npm:pi-jefferson` installs the tarball under pi's npm
root (`package-manager.js` `getNpmInstallRoot`: project scope `<cwd>/.pi/npm`, otherwise
`<agentDir>/npm`). At startup, `resolvePackageSources` → `collectPackageResources(<installed root>)`
(package-manager.js:1848):

- If the package's `package.json` has a `pi` field with an `extensions` array
  (`readPiManifest`, pi-manifest.js) → load **exactly the declared paths**, each resolved
  with `resolve(root, entry)` relative to the package root.
- **Otherwise — and this is pi-jefferson's case, which has no `pi` field** — fall back to the
  convention directory `<packageRoot>/extensions/` → `collectAutoExtensionEntries`
  (package-manager.js:~380): every direct `.ts`/`.js` file, plus one-level subdirs via
  index or subdir `pi` manifest. `.gitignore`d paths and `node_modules` are skipped.

**Can a manifest point outside the conventional directory?** Yes. `docs/packages.md`
documents it verbatim: *"Use an explicit manifest when resources live elsewhere"* with
`"pi": { "extensions": ["./src/extension.ts"] }`, *"Paths are relative to the package root.
Arrays accept glob patterns and exclusions."* The code confirms: entries are
`resolve(root, entry)` / `expandPackageGlob(entry, root)` with no containment check. So a
manifest entry may name `src/…`, a nested dir, or a glob — anything the `files` array ships.

### 2. A test file beside the extension file

If a `.test.ts` file sat in `extensions/`, the host would treat it as an extension at **every
pi start** (local dirs) or **every start of every installer** (shipped in the tarball, since
`files` includes the whole `extensions/` directory). What actually happens, per
`loadExtension` (loader.js:~520): jiti imports the module — so its top-level code runs,
including `node:test` imports and `test()` registrations — and because a test file exports no
default factory function, the load returns `Extension does not export a valid factory
function: <path>`, surfaced as a startup diagnostic (`Failed to load extension "<path>"`,
main.js:654) rather than a crash. The repo's own `tests/jefferson.test.ts` header and the
README state the same rule independently. A test file in `tests/` is invisible to all of
this: no discovery path looks there, and it is not in `files`.

### 3. Does the host execute TypeScript directly? Yes.

`loader.js` opens: *"Extension loader — loads TypeScript extension modules using jiti."*
`loadExtensionModule` builds jiti (2.7.0) and does `jiti.import(extensionPath, { default: true })`
— transpile-on-import, **no build step, no type checking at load time**. Imports of
`@earendil-works/*` inside an extension resolve through the host's alias map
(`getAliases`, loader.js:~50) to the **host's own module instances** — which is exactly why the
README says host-provided packages must be `peerDependencies`, never `dependencies`
("A physical copy bypasses pi's module mapping and duplicates classes and registries; pi
reports a warning when it sees a manifest configured that way").

Permitted syntax, from evidence: the same `.ts` files are also executed by `npm test` via
`node --test` on Node 26 (CI pins node 26), i.e. Node's native type stripping, which accepts
only erasable TypeScript syntax (no enums, no non-erasable namespaces, no parameter
properties, no legacy decorators). Host loading is stricter-checked nowhere — jiti does not
type-check — so the tests/typecheck are the only enforcement of types; syntax must clear
both jiti (permissive) and Node type stripping (erasable-only).

### 4. What the published tarball contains, and what controls it

Verified by running `npm pack --dry-run`:

```
LICENSE, README.md, extensions/jefferson.ts, package.json   (4 files, 3.2 kB)
```

Controlled by: the `files` array in `package.json` (`extensions`, `README.md`, `LICENSE`),
plus npm's automatic inclusions (`package.json`; README/LICENSE would be included even
unlisted). `tests/`, `openspec/`, `.github/`, `.pi/`, `tsconfig.json`, and `node_modules`
do not ship. CI additionally **asserts the exact list**
(`ci.yml`: `npm pack --dry-run --json` compared against
`["LICENSE", "README.md", "extensions/jefferson.ts", "package.json"]`, failing the build on
any change — "Catches a `files` mistake before it reaches a publish, where it is permanent").

### 5. What CI checks and what it does not

`.github/workflows/ci.yml` (on PR and push to `main`): checkout → Node 26 + npm cache →
`npm ci` → `npm run typecheck` → `npm test` → the tarball-contents assertion above.

It does **not** check: lint or formatting (no tool configured); coverage; any integration
step that installs the packed tarball into a real pi and verifies it loads (the load path is
exercised only indirectly, by unit tests against a fake `ExtensionAPI`); `npm publish` itself
(that is release.yml's job, which re-runs `npm ci`/typecheck/test before publishing).
`CODEOWNERS` notes a ruleset on `main` requiring code-owner review, and the README says main
accepts no direct pushes — both are GitHub settings, not verifiable from the tree.

`release.yml` (push to `main`): computes the bump from PR labels (`release:major|minor|patch`,
default patch) → `next-version.mjs` derives the version from the highest `v*` tag reachable
from `HEAD~1` (tags, not `package.json`, are the source of truth) → `npm version` syncs the
manifest → publishes with OIDC trusted publishing + provenance → tags and creates the GitHub
Release. Idempotent on re-run.

## The feature path: a new ordinary source file, disk → host execution

1. **Disk.** The file is added under `extensions/` (e.g. `extensions/foo.ts`), a subdir with
   `index.ts`, or any location named by a `pi.extensions` manifest entry.
2. **Typecheck.** `tsconfig.json` `include` picks up `extensions/**/*.ts`; `npm run
   typecheck` (`tsc --noEmit`) covers it. There is no compile step — the `.ts` file itself
   is the shipped artifact forever.
3. **Tests.** `npm test` (`node --test`) discovers `**/*.test.ts` (verified: it finds
   `tests/jefferson.test.ts` and passes 2/2) via Node 26 type stripping; tests import the
   source by relative path (`../extensions/jefferson.ts`, enabled by
   `allowImportingTsExtensions`).
4. **Pack.** `files: ["extensions", …]` puts the file in the tarball; `ci.yml` fails CI if
   the tarball list changes without updating its expectation.
5. **Install.** A user runs `pi install npm:pi-jefferson`; npm resolves the tarball into pi's
   npm root (`<cwd>/.pi/npm` or `~/.pi/agent/npm`), per `getNpmInstallRoot`.
6. **Discovery.** At pi start, settings' `packages` entries → `collectPackageResources` → no
   `pi` field → convention dir `extensions/` → `collectAutoExtensionEntries` → the file is
   added as an extension resource.
7. **Execution.** `discoverAndLoadExtensions` → `loadExtension` → jiti transpiles the `.ts`
   in-process and imports it; `@earendil-works/*` imports alias to the host's own modules;
   the **default export must be a function**, which `initializeExtension` calls as
   `factory(ExtensionAPI)`; registrations commit onto the runtime. Missing/invalid default
   export ⇒ load diagnostic, not a session crash.

**Directories that ship:** `extensions/` (whole tree, verbatim, `.ts` as-is).
**Directories the host loads:** only what discovery finds — for this package, the installed
`extensions/` dir (or manifest-declared paths); locally, `.pi/extensions/` and
`~/.pi/agent/extensions/`, neither of which this repo uses.
**Directories the host must never load:** `tests/` (not shipped, not a discovery location —
this is why tests live there), plus `openspec/`, `.github/`, `.pi/`, `tsconfig.json` — none
ship, none load.
