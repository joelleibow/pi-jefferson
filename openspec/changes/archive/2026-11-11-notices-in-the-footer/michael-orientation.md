# Orientation — notices-in-the-footer (consult, not a gate)

Baseline measured on `notices-in-the-footer` at 9cb540d: `pnpm typecheck` clean, `pnpm test` 360/360. Working tree: only `.openspec.yaml` modified. Chidi's citations are to Joel's global pi 1.5.2; the repo compiles and tests against the devDependency pin 1.4.0 (`node_modules/@earendil-works/pi-coding-agent/package.json`). I re-checked every load-bearing claim below against 1.4.0 and cite its line numbers; the notice code, thresholds and event order are the same in both.

## 1. Decisions on record

**Joel's rulings (binding):**
- R1 2026-11-10 (owner-rulings.md:7-8): the notices show in the footer *instead of* the transcript, visible for a *configurable* time, then *fade out or disappear*; ends with his live check. The ending is explicitly left open (:10).
- R2 2026-11-05 "pi is the source of truth" (archive/2026-11-05-configurable-instruments/owner-rulings.md:14): his words are *"those all should be able to come from pi, right?"*; the gloss is nothing reads the terminal, nothing shells out. Re-deriving a notice from pi's own `message_end` payload, entries and model prices is inside this ruling. Copying pi's *rule* is a cost (see §2), not a breach.
- R3 2026-11-07 configure no more than necessary; R4 2026-11-03 don't invent; R5 2026-11-08 every shipped datum instrument has a default label, a word with a colon; R6 vocabulary; R7 `~/.pi/agent/pi-jefferson.json` never edited; R8 breaks are cheap pre-1.0.

**Approved designs/rulings of mine that bind:**
- D-a (archive/2026-11-10-instruments-for-every-datum/design.md D3, my PL4 ruling michael-pl4-4-r1.json): a process API is injected at the composition root (`startup.ts` passes `homedir`); `data/` names no process API. A clock and a scheduler for this change take the same seam — `startup.ts` supplies `now`/`setTimeout`-shaped readers beside `homedir` and `requestRender` — rather than `data/` calling globals.
- D-b (same design D1; living store spec :206-215, :322-345): a new datum enters through the store and the feed; every subscription joins the feed's single `release`; a footer-only datum attaches from the factory.

**Standing records (record, not prove):** living statusline spec :348-353 (*an instrument* MUST NOT subscribe, poll, cache host data); living store spec :35-37 (reads synchronous, never request a repaint), :72-75 (freshness never exceeds the host's delivery), :192-198 (the store requests the repaint itself), :299-301 (statuses: "claim no freshness beyond the last render the host requested, and MUST NOT poll"), :244-250 (every subscription released on dispose).

**Is a Jefferson timer a contradiction of a ratified decision?** No. I traced the "no timers" lineage: (i) council-accepted feedback in session-data-store (archive/2026-11-03-session-data-store/council.md:20, :68) — that change's four owner rulings (its owner-rulings.md) say nothing about timers; (ii) a *host fact* in that design ("the host re-renders on request, never on a footer-specific timer", design.md:47); (iii) my own orientation of the last change ("spec :361 forbids polling") and the Non-Goal it produced (archive/2026-11-10-instruments-for-every-datum/design.md:27 "a repaint the extension requests on a timer"). None is Joel's. The living specs forbid *polling* — asking the host again whether something changed — by the instrument (:348-353) and by the store for statuses (:299-301). A timer that expires a notice Jefferson already holds asks the host nothing: the deadline is known when the notice arrives, and one `setTimeout` to it is a scheduled local state change, not a poll. So the timer revises a non-goal and a council preference, and R1 is the strong evidence that justifies it. The design must say so in those words and add one spec sentence, because the specs are silent: *the store may advance a datum Jefferson itself holds on a clock the root supplies and request a repaint for it; the host reads that repaint incidentally triggers (`sample()` reads `ctx.getContextUsage()` and statuses, session-data-store.ts:89-95) are no freshness claim.* A fade is where this needs care: N timed repaints are N whole-tree renders, each re-sampling the host — honest only because the spec already states statuses/context as "as of the render".

**What the design must also name as revised:** the Non-Goal line in archive/2026-11-10 design.md:27 (archived; ADR per AGENTS.md if a rule is being retired — but the rule was never in a spec, so a design decision with the citation suffices).

## 2. Traps, measured

**T1 — There is no suppression.** `showCacheMissNotices` appears in 1.4.0 `dist` only in settings files, `settings-selector.js:336` and `interactive-mode.js` (private methods at IM:3295-3380, called from the session-event switch after extension handlers). No extension event, hook or option exists (grep of `core/extensions/types.d.ts`: none). So "instead of the transcript" is true only while the setting is off — pi's default (`settings-defaults.js:27`). Jefferson must not write pi settings. Consequence for the contract: placing the `notice` instrument is the switch; a user who also turns pi's setting on sees both. (Joel's call, §3.)

**T2 — The rules must be copied; they cannot be imported.** `package.json` `exports` is `{".", "./rpc-entry"}` only (verified); Node enforces it, so `core/cache-stats.js` is unreachable, and `index.d.ts:5` exports only two cache-warmer *types*. `detectMiss` + `scan` (cache-stats.js:14-89) and the constants `CACHE_TTL_MS = 5m` (:5), `NOISE_FLOOR_TOKENS = 1024` (:7, not exported), and the display gate `missedTokens < 20_000 && missedCost < 0.1` (IM:3367) would be Jefferson's copies, with provenance pinned in a test. Precedent exists: `components/instruments/status.ts:12-14` copies pi's status sanitize rule. The scan can ride the store's existing leaf-keyed `scanTotals` (session-data-store.ts:41-59, :89-92) — one pass yields totals and the "previous request" record — which is the make-the-change-easy move. Drift risk: pi changes a threshold, Jefferson's notice fires differently, and no test can see it; the design states this as a consequence.

**T3 — Event order.** `agent-session.js:752-767`: extension handlers run (`_emitExtensionEvent`), then public listeners, then `appendMessage`. So in a `message_end` handler `ctx.sessionManager.getEntries()`/`getBranch()` end at the previous message — exactly what `detectCacheMiss` requires (cache-stats.js:107-110) and what the thinking-drop count assumes (IM:3338-3346). `message_end` also fires for user/toolResult/custom messages; filter `role === "assistant"` and skip `stopReason` aborted/error as pi does (IM:2859-2866). The leaf-keyed scan at that instant is the previous leaf: correct by construction.

**T4 — Events per kind (1.4.0 types.d.ts):** cache miss and dropped thinking → `message_end` (:849) + `ctx.modelRegistry.find` (:225; model-registry.d.ts:29) for the `cacheRead === 0` price fallback only; compaction → `session_compact` with `compactionEntry.usage` (:614-615; session-manager.d.ts:54); branch summary → `session_tree` with `summaryEntry?.usage` (:665-668; :67). **Cache warm has no extension event**: `cache_warming_decision` is pre-refresh; a completed warm is only a `usage` entry with `kind: "cache_warm"`. Jefferson could notice it only at the next render's leaf-keyed scan, with the clock starting at detection, not at the warm. Either drop warm or state that freshness honestly (Joel's, §3).

**T5 — Disposal.** Host paths new/resume/fork and the `/reload` command call `resetExtensionUI` → `setExtensionFooter(undefined)` → our `dispose` (`release`) before the session is invalidated (IM:366-368, :1898-1908, :5337; agent-session-runtime.js:111). **`ctx.reload()` does not**: agent-session.js:2998-3002 emits `session_shutdown` then `oldRunner.invalidate()`; `resetExtensionUI` never runs; the old footer stays installed until the new `session_start` (:3028) runs `releasePrevious?.()` and `setFooter` again. Jefferson registers no `session_shutdown` handler today (rg over `extensions/`: none). A notice timer firing in that window calls `requestRender`, the render calls `sample()` → `ctx.getContextUsage()` → `runner.assertActive()` throws (runner.js:678-680). Required: the pending timer is cleared in `release`, and `startup.ts` registers `session_shutdown` → `releasePrevious?.()` (pi docs extensions.md:254-256 require it). This is the existing release called from one more place, not a new noun; it also closes a pre-existing exposure.

**T6 — Instrument and store rules.** The notice is a datum in `Readings` (store spec :9-12: "a datum an instrument needs MUST be added to the store"); the instrument only reads (`$notice` resolver), `variableFg` by kind reproduces pi's colours — `warning` for miss/compaction/branch/thinking, `dim` for warm (IM:3300, 3314, 3351, 3380) — the way `thinking.ts` already does. Readings are a fresh object per `sample()` (store.ts:93-98) and cells key their text cache on sample identity (row-renderer.ts:40-52), so a timer that changes store state then requests a render is enough. The timer and the `message_end`/`session_compact`/`session_tree` subscriptions live in the feed and join `release` (D-b). The configurable duration is one option key on the declaration (`options: [...FOUNDATIONAL_OPTIONS, "<key>"]`), parsed in `readInstruments` (configuration.ts:76-123) on the `rowGap` bounded-integer precedent (:65-68, :253-265).

**T7 — Width-0 rule and the empty cell.** A notice's text does not depend on width; a fade changes only colour, so `visibleWidth` is unchanged — the width-0 ≡ width-200 guard (tests/instrument.test.ts:337-361) passes if the new instrument is added to its expected list. The cell is empty most of the time and "takes none" (statusline spec :43-45, :103-110); when a notice arrives the row re-seats (row-renderer.ts:118-124) and a fill cell or `$bar` in the same row shrinks by the notice's width, then grows back on expiry. That jump is ADR 0007's consequence and must be stated. A notice is one line; long texts ("Cache miss after model switch: 125.3k tokens re-billed (~$0.38)" ≈ 60 cols plus label) clip in a narrow cell, per the one-line ruling.

**T8 — Fade mechanics.** `ThemeStyle.fg` accepts `ThemeColor | Color` in 1.4.0 (theme.d.ts:14-17) and `mixColors` is exported from pi-tui (colors.d.ts:64), so a concrete-colour fade is type-possible — but the theme exposes no background colour (theme.d.ts getters: `appearance`, `colors`, `getColorMode`; the background it mixes dim tokens toward at theme.js:179-183 is private), a user-configured `style.fg` would need mixing too, and 256-colour terminals quantize the ramp. A token-step fade (`warning` → `muted` → `dim` → gone, pi's own documented working-indicator pattern) needs no colour maths, respects themes, and fits `variableFg` as it is. Either fade needs a cadence: an interval that runs only while a notice is fading and stops when none is.

**T9 — Default label.** R5 binds: the instrument ships a default label, word + colon; pi's texts already begin "Cache miss:" etc., so the default reads `Notice: Cache miss: …`. A user sets `label: ""` to drop it (2026-11-07 ruling).

**T10 — Overlap.** `message_end` can yield a thinking-drop and a miss together (IM:2864-2865); compaction then a miss follows. One `notice` datum (newest replaces) is the smallest; a queue is mechanism with its own timing rules.

## 3. Calls that are Joel's

1. **Fade out, disappear, or both.** *Disappear*: one `setTimeout` per notice, one repaint, no colour code; ~the smallest change. *Fade*: a cadence while fading (N whole-tree renders, each re-sampling the host), a colour ramp (token-step: 3 visible steps, theme-safe; concrete: no public background, 256-colour quantizes), and either a second configurable or a fixed ratio against R3. *Both*: a third option. Fade ⊇ disappear, so "fade only" also satisfies R1. I would ship disappear first and let him judge token-step fade at the live check R1 already requires.
2. **The contract when pi's setting is on.** Jefferson cannot suppress the transcript lines (T1). Does it ignore pi's setting (instrument presence is the switch; double-show is the user's choice), or warn once at session start via `pi.getSettings()` (available, no change event)? I would ignore and document — R4.
3. **Which kinds ship.** Cache warm has no event (T4): drop it, or show it when a later render's scan finds it with the clock starting then. I would drop it from this change and say why.
4. **Overlapping notices** (T10): newest replaces, or a queue each with its own duration. I would replace.
5. **Default duration and label text** are the design's with his live check; he should know they are defaults, not rulings.

## 4. The strongest challenge

This asks Jefferson to re-derive, from pi's data, a diagnostic pi already computes but does not export, behind a setting pi defaults to off and offers no hook to suppress — so "instead of the transcript" holds only for users who never turn the setting on, and the four rules Jefferson must copy (1024-token floor, 20k/$0.10 gate, 5-minute TTL, the thinking-drop delta) drift silently the next time pi tunes them, with no test able to tell. It puts the first clock into a footer whose every freshness promise is "as fresh as the host, no fresher", for a line the user sees for a few seconds and cannot act on, in a cell that is empty almost always yet shifts its row when it fills; and one of the five notices Joel named cannot be delivered on time at all. Against that: every input is pi's (R2 holds), the miss detection rides the store's existing leaf-keyed scan, and the smallest version — disappear, one `$notice` variable with pi's text and colours, one timeout cleared in `release`, a `session_shutdown` handler, one bounded option — is a few dozen lines plus pinned thresholds. The narrow path is that version, with warm dropped and fade deferred to what he sees live.
