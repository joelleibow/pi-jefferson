## Findings

### 1. pi-tui vertical stack

- **`VStack` has a `gap` option.** `StackOptions { gap?: number; align? }` — `components/stack.d.ts:15-18`. Constructor normalizes it to a non-negative integer, default 0 — `stack.js:15` (`normalizeSize(options.gap, 0)`, floor, NaN→0, line 6-8).
- **What it inserts (render path).** `VStack.render` pushes `""` (empty, unstyled strings) `gap` times before every visible entry except the first — `v-stack.js:13-17`. The unit is terminal lines. Gap lines carry no styling or width padding.
- **Hidden / zero-height children.** Only entries whose `visible(viewport)` callback returns false are dropped, before gaps are counted (`stack.js:55-57`, `v-stack.js:9`), so a hidden entry produces no gap. An entry that is visible but renders zero lines still counts as an entry: it still receives a gap before it (`v-stack.js:13-22`), so a gap line appears even though the child adds nothing. The stack does not look at line content, so a child rendering `""` is a normal 1-line child.
- **Changing gap after construction.** `gap` is `protected readonly` (`stack.d.ts:21`), assigned only in the constructor (`stack.js:15`); there is no setter. Changing it means constructing a new stack. (Plain JS can mutate it, but the types forbid it; unsupported.)
- **Alt-screen layout path.** In `layout.js:96-116` (the fullscreen layout, used with `setLayoutRoot`), `gapTotal = (entries.length - 1) * gap` is added to natural height (97, 101) and each child is placed at `childY += size + gap` (114). `allocateStackSizes` subtracts the gaps from available space before grow/shrink (`stack.js:99-109`). The gap there is empty screen rows, not strings. `VStack.render` itself calls `allocateStackSizes(..., undefined, gap)` so gap does not affect sizes in the render path.
- **HStack** `gap` is horizontal columns (`layout.js:155` `childX += childWidth + node.gap`); same option name on both stacks. HStack `render` is unchanged between versions.
- **Spacer.** `new Spacer(lines = 1)`; `render` returns that many `""` lines; `setLines(n)` changes it after construction — `components/spacer.js:6-21`. README: "Empty lines for vertical spacing" (`README.md:652-657`). A Spacer is a normal child, so between two rows it works like a gap of its own, mutable.
- **Padding.** `Text(text, paddingX = 1, paddingY = 1, bgFn)` and `Box(paddingX = 1, paddingY = 1, bgFn)` add `paddingY` lines above/below (`text.js:8-16,60+`, `box.js:14-17`); Text pads with space-filled full-width lines (`" ".repeat(width)`), and renders nothing at all for empty/whitespace text (`text.js:44-52`). **There is no per-child margin option** on `StackEntryOptions` (`basis, grow, shrink, minSize, maxSize, visible` only — `stack.d.ts:3-10`).
- **Other.** `basis`/`minSize` on a stack entry can force a child's height (`allocateStackSizes` pads short children with `""`, `v-stack.js:20-21`), so an entry with `minSize: 2` and one line of content has a trailing blank line. `Container.render` just concatenates children (`tui.js:137-148`); it has no gap.
- **1.4.0 vs 1.5.0.** `diff` of `components/stack.js`, `v-stack.js`, `h-stack.js`, `spacer.js`, `box.js`, `stack.d.ts`, `v-stack.d.ts`, `layout-node.js` — identical. `layout.js` differs only in Kitty image cropping inside scroll views (`getMaxKittyImageRows`); not about gaps. Other 1.5.0 diffs are in editor, markdown, select-list, settings-list, text.js, fuzzy, keybindings, index (not diffed in depth; `text.js` differs, so Text padding behaviour in 1.5.0 was not compared line by line). Stack/gap/Spacer behaviour: no difference found between 1.4.0 and 1.5.0.

### 2. pi's footer contract

- `ctx.ui.setFooter(factory)` → `setExtensionFooter` (`interactive-mode.js:2043-2060`): clears `footerContainer`, calls `factory(tui, theme, footerData)`, `addChild`s the result, `requestRender()`. The docs show only `render(width): string[]` + `invalidate()` (`docs/extensions.md:2907-2910`); nothing is documented about height, spacing, or blank lines.
- **Height.** `footerContainer` is a plain `Container` (`interactive-mode.js:414`), which concatenates children's lines without trimming (`pi-tui tui.js:137-148`). In regular (scrollback) mode the footer is the last child of the TUI (`interactive-mode.js:710-717`) and no height cap was found. In fullscreen mode `chat-viewport.js:18` gives the footer `{ shrink: 1, minSize: 0 }` in the dock VStack, so the dock can shrink the footer, down to 0 rows, when the terminal is short.
- **Trim / collapse / empty line.** I found no code in the footer path that trims, collapses or specially treats `""` lines; an empty string is a line like any other. (grep of `tui.js` for trim/trailing logic found none in the render path; not an exhaustive audit of the differential renderer.)
- **Spacing around the footer.** `interactive-mode.js:710-717` mounts containers back to back (…`editorContainer`, `widgetContainerBelow`, `footerContainer`); I found no spacer added by pi above or below the footer.
- **Built-in footer** (`components/footer.js`): `const lines = [pwdLine, dimStatsLeft + dimRemainder]` (line 251), plus one optional extension-status line pushed at ~261, `return lines` (262). **No blank line between its lines**; rows are directly adjacent. Same in 1.5.0 (this is the installed file).

### 3. How comparable tools express vertical space between lines

| System | Vertical space between lines | Name | Default | Unit | Scope |
|---|---|---|---|---|---|
| Starship | Line break is a module: `$line_break` in `format`; `[line_break] disabled = true` collapses the prompt to one line ("The `line_break` module separates the prompt into two lines"). Separate top-level `add_newline` "Inserts blank line between shell prompts". | `line_break`, `add_newline` | `add_newline = true`; `line_break` enabled, in `$all` before `$jobs…$character` | a newline / one blank line | `add_newline` is global, before each prompt, **not** between prompt lines. Space between lines = put extra `\n` or `$line_break` in `format`; no gap setting. |
| powerlevel10k | `newline` is a segment in `LEFT_PROMPT_ELEMENTS` that starts a new line (`# newline # \n`). `POWERLEVEL9K_PROMPT_ADD_NEWLINE` "Add an empty line before each prompt". | `newline` segment, `PROMPT_ADD_NEWLINE` | `true` in classic config | one empty line | Global, before the prompt; no between-lines setting. `MULTILINE_FIRST_PROMPT_GAP_CHAR` is a horizontal filler on line 1, not vertical. |
| tmux | `status [off|on|2|3|4|5]`: "2, 3, 4 or 5 more rows"; each row's content from `status-format[]`. | `status`, `status-format[n]` | `on` (one row) | rows | No gap option. A blank row = an empty `status-format[n]` (issue #1886 shows this). Rows are adjacent. |
| lualine / Neovim | No multi-row statusline; open feature request #1123 "Have more than one row (multiple status lines)". Statusline, tabline and winbar are separate single lines. | none | n/a | n/a | `padding` option (default 1) is horizontal only (`lualine.txt:531-532`). |
| pi-powerline-footer | Rows: primary bar plus a `secondary` row/group (`layout.secondary`, customItems `position: "secondary"`). `padding` (0-8, default 1) is the outer spaces on each edge of every row. `secondaryOverflow: "wrap"` continues extra lines below. | `padding` (horizontal), `secondary` | padding 1 | columns | **No setting found for vertical space between rows** (README says padding does not change segment spacing or editor spacing; no "gap"/"spacing between rows" match). |
| CSS (vernacular) | `row-gap`, with shorthand `gap` ("sets the gaps (also called gutters) between rows and columns"), plus `column-gap`. | `row-gap` / `gap` | initial `normal`: computes to `0` in flex/grid, `1em` in multi-column | length (px, em, ch...) | Per container, one value for all rows. |

- **De facto.** Prompt tools (Starship, p10k) model space as a *newline*: a `line_break`/`newline` element in the layout, plus a global `add_newline` boolean (default true) for the blank line *before* the prompt, not between its lines. Status bars (tmux, lualine) have no inter-row spacing; a blank row is an empty row. The only widely used name for a configurable between-rows distance is CSS `row-gap`/`gap` (and pi-tui's own `VStack` `gap`, which shares the name). No statusline I checked has a "gap between rows" option. Where space between lines exists, it is either an explicit empty row/element or the global default.

- **Assumption checked**: "the footer is a pi-tui `VStack` of `HStack` rows" — consistent with the APIs found; I did not read this repo's code.

- **Unknown / not verified**: (a) whether the differential renderer in pi-tui `tui.js` does anything to trailing or empty lines beyond the Container path (not audited end to end); (b) whether a fullscreen-mode footer with `shrink: 1, minSize: 0` drops gap lines first on a short terminal (layout logic read, not run); (c) Text.js differs between 1.4.0 and 1.5.0 and was not compared line by line; (d) pi-powerline-footer docs were searched for gap/spacing only in the README, not in its source; (e) lualine `winbar`/tabline stacking was not tested; the "no multi-row" claim rests on issue #1123 (open, 2023-24) plus the option list.

## Addendum 1 — the row above the footer

Evidence only. `$PI` = `~/.local/share/fnm/node-versions/v26.8.1/installation/lib/node_modules/@earendil-works/pi-coding-agent` (1.5.0, what Joel runs). The repo's 1.4.0 copy is `node_modules/@earendil-works/pi-coding-agent`. Line numbers are `dist/modes/interactive/interactive-mode.js` unless noted.

### Q1. Layout between editor and footer

- **Order (1.5.0).** `mountInteractiveTui` adds, in order: `documentContainer`, `pendingMessagesContainer`, `statusContainer`, `widgetContainerAbove`, `editorContainer`, `widgetContainerBelow`, `footerContainer` (lines 710-717). Fullscreen dock `chat-viewport.js:12-19` uses the same order: pendingMessages, status, widgetsAbove, editor, widgetsBelow, footer.
- **`statusContainer` is not above the footer.** It sits *above* the editor and holds the working/idle indicator (lines 396, 1874-1897); it is unrelated to `setStatus`. Between editor and footer there are only `widgetContainerBelow` and `footerContainer`.
- **Spacing pi inserts.** `renderWidgetContainer(container, widgets, spacerWhenEmpty, leadingSpacer)` (lines ~2024-2040): `renderWidgets` calls it for above-widgets with `(true, true)` and for below-widgets with `(false, false)` (lines 2021-2022). So `aboveEditor` gets a one-line `Spacer(1)` (even when empty, and before widgets), while `belowEditor` gets **no spacer, empty or leading, and no trailing spacer**. Below widgets are added as bare children (`container.addChild(component)`). The footer container adds nothing around the footer (`setExtensionFooter`, lines 2043-2060). Net: a `belowEditor` widget's last line is directly adjacent to the footer's first line; pi puts nothing between them.
- **`setWidget` default** is `aboveEditor` (`setExtensionWidget`, line 1941; `core/extensions/types.d.ts:47-52`). String-array widgets are wrapped in `Text(line, 1, 0)` and capped at `MAX_WIDGET_LINES = 10` (lines ~1951-1958, 2008); factory widgets are used as given. Widgets with the same key replace each other across placements (lines 1942-1952).
- **Can a footer know something sits above it?** The factory gets `(tui, theme, footerData)` and `render(width)` gets only a width (`types.d.ts:122`; `docs/extensions.md:2907-2910`). `footerData` is `Pick<FooterDataProvider, "getGitBranch" | "getExtensionStatuses" | "getAvailableProviderCount" | "onBranchChange">` (`core/footer-data-provider.d.ts:63`). None exposes widgets or other components' heights. I found no API for a footer to learn that a widget exists above it; `tui` is the whole TUI object, and I did not audit it for a public way to enumerate the widget containers (unknown).
- **Fullscreen**: the dock VStack gives the footer `shrink: 1, minSize: 0` and `widgetsBelow` `shrink: 1, minSize: 0` (`chat-viewport.js:17-18`); on a short terminal either can be squeezed.
- **1.4.0.** Same: `renderWidgetContainer` (1938-1952) and the `(true, true)` / `(false, false)` calls (1934-1935); mount order at 695-698, dock at `chat-viewport.js:18`. No difference found.

### Q2. Built-in footer vs custom footer

- **Built-in footer and `setStatus`.** `setExtensionStatus(key, text)` only stores text in the `FooterDataProvider` map and requests a render (lines ~1857-1862; `core/footer-data-provider.js:127-135`). The *built-in* `FooterComponent` reads `getExtensionStatuses()`, sorts by key, runs each through `sanitizeStatusText` (newlines/tabs → space, collapse spaces, trim), joins with a space, truncates to width, and pushes it as **one extra line after the pwd and stats lines** (`components/footer.js:253-261`, lines 10-16 for the sanitizer). 1.4.0: identical (footer.js 253-262).
- **Built-in footer and `belowEditor` widgets.** The built-in footer does not render widgets at all; widgets live in `widgetContainerBelow`, a sibling above the footer container (above). Widgets and statuses are independent channels.
- **Custom `setFooter`.** `setExtensionFooter` replaces the footer container's child with the extension's component (lines 2043-2060); pi's `FooterComponent` is no longer rendered, so pi no longer shows the status line. Nothing else renders `getExtensionStatuses()`, so a custom footer drops `setStatus` text unless it renders it itself. The API exists for that: `footerData.getExtensionStatuses(): ReadonlyMap<string,string>` (`footer-data-provider.d.ts:38,63`); `types.d.ts:116-121` documents "The factory receives a FooterDataProvider for data not otherwise accessible: git branch and extension statuses from setStatus()". There is **no subscription for status changes** (only `onBranchChange`); `setExtensionStatus` calls `ui.requestRender()` so the footer re-renders and can read the map during `render`. `belowEditor` widgets are unaffected by `setFooter`; they keep rendering above the custom footer.
- **1.4.0.** Same `ReadonlyFooterDataProvider` (`footer-data-provider.d.ts:63`, `getExtensionStatuses` at 38) and `setFooter` doc. No difference found.

### Q3. Blank line at the top of a footer component

- By the evidence: yes, expected. `footerContainer` is a plain `Container`; `Container.render` concatenates children's lines with no filtering (pi-tui `tui.js` Container.render, 1.4.0 lines 137-148; same file in 1.5.0 — `tui.js` identical in the regions read). The footer's `""` first line therefore occupies a row between the last `belowEditor` widget line and the footer's first real row; pi inserts no spacer there that it could merge with, and widgets add none below.
- In the regular (scrollback) renderer, nothing found trims empty lines (see main report, unaudited renderer caveat). In fullscreen, the layout path measures `render().length` for the footer (`layout.js` `measureHeight`), so a leading `""` counts as one row of height; `shrink: 1, minSize: 0` means that row can be squeezed away on a short terminal along with the rest.
- **Not run.** I have not rendered this live in pi; this is read from source. Whether a leading blank row also appears when no widget is present (i.e. a blank above the footer under the editor) follows from the same code: there would be a blank row directly below the editor. `widgetContainerBelow` with no widgets renders zero lines.
- pi-subagents context: `fleet-status.js:638` calls `ctx.ui.setWidget(FLEET_STATUS_WIDGET_KEY, (tui, theme) => …)` with no placement per the brief (line numbers 45/516 given by the conductor; I only confirmed 638, 1060, 1095 in the file). Per the brief it is `belowEditor`; I did not verify the placement argument in that file.
