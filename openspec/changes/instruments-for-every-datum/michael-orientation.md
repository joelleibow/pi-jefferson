Living spec: openspec/specs/statusline/spec.md:361-364 ("An instrument MUST NOT subscribe … read the terminal, run a command, or derive data the store can hold") and :385-389 ("A datum the host does not expose … is not implemented").

D. **A datum enters the store, not the instrument.** openspec/specs/session-data-store/spec.md:11-14 — "The store MUST hold exactly the data the extension's instruments display … A datum an instrument needs MUST be added to the store." Its "holds nothing else" scenario (:16-21) and its exclusion scenario (:28-32: "the git branch, extension statuses, or the provider count — the store does not hold it, and takes no subscription for it") both become false the moment a new instrument lands; the delta MUST rewrite them (the exclusion scenario is the mirror image of this change). Archive origin: archive/2026-11-03-session-data-store/owner-rulings.md:55-59 — "the instrument that needs one arrives with the store field it needs."

E. **Freshness is stated per datum.** session-data-store/spec.md:78-83 — "For every datum it holds, the store MUST state how current that value is, and MUST NOT claim freshness greater than the host's own delivery." Three shipped patterns exist: seed-at-start (cwd), seed+push (model, thinking), per-sample read (context usage, keyed scan). Every new datum must be assigned one of those three, with the host read or event named.

F. **Pushes repaint from the store; released on dispose.** session-data-store/spec.md:198-204 and :222-226. ## 2. Traps (measured where possible)

**Growing the store and the feed.** `Readings` (session-data-store.ts:16-23) and `sample()`'s all-unknown literal (:72) are two spellings of the field list; the test `assert.deepEqual(Object.keys(sample), [...6 names])` (tests/session-data-store.test.ts:55) is a third. The spec's "holds … and nothing else" scenario (:16-21) is a fourth, and the exclusion scenario (:28-32) is its negation. Each new datum touches all of these — the delta should state the field list once and reference it, not re-enumerate. The feed's `release` (feed.ts:43-51) is hand-listed; every new subscription must be added there or it leaks past dispose (spec :222-226). `dispose()` (store.ts:103-109) must also drop any new cached value.

**Branch wiring is a lifecycle trap, not a data trap.** `footerData` exists only as the `setFooter` factory's third argument (types.d.ts:111); today `installFooter` (footer-setup.ts:22) declares a two-arg factory and the store is built *before* the footer, in `feedSessionData` (startup.ts:46 then :57). Measured: the host invokes the factory synchronously inside `setFooter` (interactive-mode.js:1957-1968), so the existing `receiveRepaint` late-binding seam (startup.ts:44-47, :62-64) is the precedent — but a new injected reader or a reordered install is design-level mechanism and must be stated in design.md, not improvised in a task. The end-to-end fake `setFooter` (tests/jefferson.test.ts:134) takes `(tui, theme)` only and must grow a `footerData` fake.

**The branch read blocks on first call.** footer-data-provider.js:111-113: `getGitBranch()` runs `resolveGitBranchSync()` → `spawnSync("git", …)` (:49) when its cache is cold. session-data-store/spec.md:41 says a read MUST NOT block. Reading the branch per sample would put a synchronous subprocess inside a render; the seed+push shape (seed once at install, update on `onBranchChange`, which the host fires after it has refreshed `cachedBranch`, :201-205) matches `model`/`thinking` and keeps samples pure. `FooterDataProvider` is app-lifetime (interactive-mode.js:408) and is re-pointed with `setCwd` on a session switch (:1570); re-seeding at `session_start` (spec :175-180) covers that if the host's order holds — Chidi should confirm `setCwd` precedes the extensions' `session_start`.

**A datum that changes mid-session with no event.** Measured against types.d.ts: the session name *has* an event (`session_info_changed`, :583-587) — seed from `ctx.sessionManager.getSessionName()` (session-manager.d.ts:178) + push. Extension statuses (`getExtensionStatuses()`) and provider count (`getAvailableProviderCount()`) have no extension-facing event; the host repaints itself for its own reasons, which spec :203-204 forbids relying on. For such a datum the only honest freshness statement is "read per sample; as current as the last render the host requested" — the same clause the spec already grants context usage (:108-113). Design must say which datums get that clause rather than invent a poller (spec :361 forbids polling).

**Unavailable outside TUI / before the first turn.** `footerData` is TUI-only by construction, which is fine: the footer is only installed under `ctx.mode === "tui"` (startup.ts:38). Before the first turn: `ctx.model` may be undefined (types.d.ts:226), `getContextUsage()` undefined, `getGitBranch()` returns `null` for "not a repo" and `"detached"` (d.ts:34), `getSessionName()` undefined until named, `getAvailableProviderCount()` is 0 until the host's async count lands (interactive-mode.js:801, :4339). `null` branch is a *genuine* value, not unknown (spec :71-74): the resolver must choose `undefined` (cell renders nothing — the host footer's own behavior, footer.js:140-143) or `""` (renders the bare label `Branch:`). The spec's label rules make these render differently; the design must pick and the delta must pin a scenario.

**Width-0 = width-200.** tests/instrument.test.ts:233-250 renders every shipped non-fill instrument at 0 and 200 and `deepEqual`s a hardcoded list of six names (:250). Every new instrument is a string value, so none should read width; the trap is the fixture: the `shapes` table (:30), `labels` (:41-44), `declarations.length === 7` (:71), `expected` (:85) and `measured` (:250) are five live counts that must all move together. And `instrumentNamed("git")`/`"branch"` are asserted *unresolved* (:78) — a branch instrument legitimately edits that expectation; the report must say so, since an edited expectation otherwise blocks.

**Default labels.** Ruling I binds every new instrument: `Branch:`, `Session:` (or whatever the noun is), etc. The living requirement at spec.md:1152 is phrased "a shipped instrument that declares a default label"; the delta should make it "every shipped instrument that displays a datum MUST declare one" so the rule is universal rather than a list that goes stale (one fact, one place).

**Name collisions.** Instrument names and variable names are separate namespaces (`tokens` instrument vs `context`'s `$tokens` already coexist, instrument.ts:84 and :95), so the collision is human, not mechanical. Two real ones: (a) `branch` in pi means two things — the git branch (`getGitBranch`) and the session-tree branch (`sessionManager.getBranch`, `branch_summary` entries, session-manager.d.ts:178; store.ts:41). An instrument named `branch` is defensible because the git change is ruled separate and the session-tree branch is not a display datum, but the spec must say which it is. (b) `git` as a name would pre-empt the separate git change with a branch-only instrument — avoid. (c) `status`/`statuses` for extension statuses collides with nothing in Joel's vocabulary (row/cell/instrument/store/label/format/style), but `widget` must not appear even though pi calls them widgets.

**`cwd` vs `path`.** Ruling J settles it for this change: renaming `path` is a separate card. Joel's live config names `path` with `$path` and label 📂 (~/.pi/agent/pi-jefferson.json, read only); a rename breaks his document and no task may edit it. The working directory is already a store datum and already has an instrument, so the *objective* (an instrument per datum) is met for it. If the host's `~`-abbreviated full path is wanted, the least-code shape is a second variable on `path` (`$cwd` or `$dir`), no new store field, no rename — but what it shows (absolute vs `~/…`) and what it is called is Joel's. Note the host's `formatCwdForFooter` reads `process.env.HOME` (footer.js:31-45) and is not exported (index.d.ts has no footer exports), so a `~` form would be Jefferson's own copy of a formatting rule — "Don't invent" cuts against it unless Joel asks.

**Compact band.** Ruling K: ratified, with the deviation recorded and the question flagged for Joel in the archived design (:809-816) and never asked. Changing is small (one constant, instrument.ts:31; spec scenario :591-592; test fixture :143-146) but it is a spec change and user-visible; it is Joel's. `formatTokens` is not importable (archived design D11 "fact 3"; confirmed index.d.ts exports no footer symbols), so "mirror the host" still means Jefferson copies the band.

**Scope line around git.** The branch is in (ruling B; brief-common). Not in: dirty tree, ahead/behind, remote, repo name (spec :385-389). The design must name the branch's source as pi's `footerData`, so the `nothing shells out` ruling is honored by Jefferson even though pi itself spawns git (footer-data-provider.js:49, :60) — that is pi's business.

**Host-only datums.** The host footer shows things no extension can read: `routedModel` (footer.js:207-211), `(sub)` via `modelRuntime.isUsingSubscription` (:163-166), `(auto)` via `autoCompactEnabled` (:172). These are not "data pi provides to an extension" and belong in the design's "deliberately not done" list with the inventory citation, so Joel's *every* is shown to be met rather than asserted. Inventory itself is Chidi's.

## 4. The strongest challenge

"Every datum" is a quantifier over an inventory nobody has produced, and three of the candidates pull against three other rulings. Extension statuses and provider count have no extension-facing change event, so the store cannot keep its promise that a displayed change repaints from the store (spec :198-204) without per-sample reads that lean on the host repainting for its own reasons — exactly what the spec forbids — or a poller, which the statusline spec forbids. The branch's first read is a synchronous `git` spawn inside pi, which the store's "a read MUST NOT block" rule did not anticipate. And the provider count is a datum pi's own footer shows only as a conditional prefix, not a value. Shipping instruments for these to satisfy "every" is the kind of invention "Don't invent what we don't have to" and "configure no more than necessary" exist to stop. The narrow correction: take the inventory to Joel as two lists — datums with a seed+push or clean sample story (branch, session name, full working directory) and datums whose only honest freshness clause is "as of the host's last render" (extension statuses, provider count) — and let him rule which side of the line "every" means, before the design commits the store to a freshness promise it cannot keep.
