# Architecture

pi-jefferson draws one footer line per configured row, with empty lines between rows. This file describes the parts and the direction they depend in. It is deliberately short: everything here is a decision a change can break, so it is worth reading before one.

## The parts

```
extensions/jefferson.ts          the entry: the only thing pi loads; it registers and calls startup
extensions/jefferson/
  startup.ts                     the install lifecycle: the command, then the session-start installs
  configuration.ts               where pi-jefferson.json lives, reads it, validates it, normalizes rows
  footer-setup.ts                pi's footer factory and the component it returns
  format.ts                      the format language every instrument shares: parses a format, asks the theme for a colour, and places $bar
  shipped.ts                     the list Jefferson registers, and the fallback and notice gate the reader needs
  instrument-contract.ts         the published types an extension imports: the two messages and a declaration
  registration.ts                what a name means, and what has registered
  registration-listener.ts       the two channels, the wait for the session's theme, the payload checks, and Jefferson's own registration
  faults.ts                      the faults this session has reported, one warning each
  data/                          the session data, the provider fields, and how the host's session and events reach it
  components/                    the parts, each directory holding only its own logic
    instruments/                 the instrument contract, the binding, and one file per instrument
    row/                         a row, its cells' width plan, and the renderer that draws it
    visuals/                     what an instrument can mix in: the bar and the timed show-and-hide
```

Logic that many parts share, and the process flow, sit directly under `extensions/jefferson/`. A part's directory holds only that part's logic. The decision behind the layout, and the alternatives it weighed, are in [ADR 0005](docs/adr/0005-source-is-laid-out-by-responsibility.md), revised by [ADR 0009](docs/adr/0009-components-hold-the-parts-and-the-bar-stands-alone.md).

**Entry.** `extensions/jefferson.ts` is the only file the host loads. It registers the extension and hands the host's API to startup, and does nothing else.

**Startup.** Owns the `/jefferson` command and the `session_start` handler. The handler first hands the registration listener the session's theme, before the mode check and before the read. A theme exists only inside a session, so a provider's registration or report that arrived earlier is copied as it arrived and waits for that theme, and only the theme can say whether a name in a format is a colour. Then it releases the previous install, reads the configuration, installs the data with what it read, and installs the footer, in that order: a notice's visible time has to reach the store when it is built, so configuration cannot wait until after the feed exists. Startup also wires the repaint callback: the footer hands the host's repaint request back out, and the data side calls it. It supplies the data side its readers: `node:os`'s `homedir`, `performance.now` for the clock a datum's instant is stamped from, and a closure over `setTimeout` and `clearTimeout` for the repaint at that instant. It is the one file that names a process API. It also runs the release on `session_shutdown`, because a reload shuts the session down without clearing the footer. It decides *when* things run; it computes nothing.

**Data feed.** Lives in `data/`. Seeds the store from the session context and the readers it is handed, and subscribes to the events that push into the store: `model_select`, `thinking_level_select`, `turn_end` and `session_info_changed`, plus `message_end`, `session_compact` and `session_tree` while a row places a `notice` cell. It hands the store its branch reader beside its entries reader, and the clock, the scheduler and the visible time the configuration file declares, which the root supplies. The branch, its change subscription and the statuses exist only inside the host's footer factory. So the feed returns an attachment beside the store, and the factory hands the footer's data through it. The attachment seeds the branch and subscribes to its change, and that subscription joins the one release with the rest. One release undoes the subscriptions, clears a pending repaint and disposes the store. The store names no host event; the feed does.

**Footer setup.** Calls `ctx.ui.setFooter` with a factory that builds the row renderer's footer, and returns the component the host expects. The factory's third parameter is the host's footer data, and setup hands it to the feed's attachment before the footer is built, so the first sample already carries the branch. Disposing that component runs the release it was given.

**Store.** Holds provider, model, thinking level, working directory, home directory, the git branch, the session's name, the extension statuses, context usage, usage totals and the one notice showing. Provider, model, thinking level, working directory, home and the session's name are seeded at `session_start`, and the branch is seeded when the footer is built. The two selection pushes update model and thinking level, a renamed session pushes its name, and a branch change pushes the branch. The attachment hands the store a statuses reader; the store calls it once per sample, holds the map as the host reported it, and treats an empty one as unknown. Injected readers sample context usage and the statuses each render, and scan the whole session's usage-bearing entries only when `(sessionId, leafId)` moves. `turn_end` compares the five totals and requests a repaint only when they change, and a notice's instant requests one repaint of its own. The notice arrives only on a push. The store stamps the instant it shows until when it arrives, converting the configuration file's seconds once there, and it never hides the notice: the store holds it until a newer one replaces it or the session is replaced. Each sample carries `sampledAt`, one clock read per render, which is the instant every timed cell compares against. The scheduler's callback requests that one repaint at the instant, re-arming for the time left when it fires early, and nothing is polled: the repaint asks the host nothing.

A read is synchronous, total, and never throws. The host disposes the footer, and through it the store, before it invalidates the session context, so a read cannot outlive its context; disposal clears the readers and cancels a pending repaint, and later samples are all-unknown. One sample per render is handed to every cell, so cost and tokens share one totals object and two status cells share one text.

**Configuration.** Resolves where the configuration file lives (the agent directory's, and a trusted project's), reads it, validates it, resolves instrument names, and normalizes rows. The configuration file's top level holds `rows`, `instruments` and `rowGap`: `rows` is a list of rows, a row is a list of instruments, and each instrument in a row carries `instrument` and optionally `align`. A row is placed by its position, and it no longer carries an identifier. The retired top-level keys — `cells`, `id` and `distribution` — reject the whole configuration file before any other check, with one fixed message that shows the shape to write. A row written as an object rejects too, and its message shows the same shape. Its result carries the rows, the `rowGap`, a warning and the visible time a notice takes. That last is `undefined` unless the rows it is about to install place a `notice` cell, so a default row and a rejected configuration file take no visible time. The optional `instruments` section configures each name once; formats, labels, styles and a composed instrument's `seconds` and `formats` are validated at read time against its declaration and the live theme, then one bound instrument per name is shared across the configuration file. The binding itself lives in `components/instruments/`. Every failure mode rejects the whole configuration file, renders the default row, and warns with a message that names what was wrong. That rule covers Jefferson's own instruments.

A name resolves through the registry, so it behaves differently. A row that names an instrument nothing has registered rejects nothing: Jefferson warns once session startup completes, renders `blank` until an extension registers the name, and renders that instrument from the next render on. Settings in the `instruments` block for a name that never registers draw no warning. A *provided* instrument's settings are checked when the configuration file and its registration are both in hand, whichever came second, and a fault refuses that instrument alone: it renders `blank` wherever a row names it, one warning names it and the fault, and the rest of the configuration file renders as configured.

**Instrument.** One declaration owns its name, variables, default format and options, and may carry a default label and a per-variable foreground token. Variables read the store and arrive already formatted. Binding resolves the label (configured, else the declaration's default), collapses its control characters once, trims it, and hands it to the format language as a leading literal segment, so the label is styled and measured like the format's own text. When a non-empty format follows, that segment ends in one space, the gap, so the label's style covers it and `$bar` counts its column; see [ADR 0006](docs/adr/0006-a-label-gets-one-gap-and-outer-whitespace-is-not-text.md). A variable's declared token can replace that segment's `fg`, unless the format names a colour for that variable, which is the strongest colour there is. A variable may also declare forms, named resolvers over the same readings with one of them the default, and a `|name` placed directly after that variable selects one: `$path|relative` renders the directory under home, a bare `$path` the basename. The declaration is the only list of a variable's forms, and parsing and rendering both read it. A declaration may also carry a composed format set: the reading that selects which format to use, one default per key, the values those formats may name, and the variable the chosen text arrives at the cell's format through. The binding resolves the selected format as plain text — no modifier and no form, so the notice stays one colour — and passes it to the cell's format as that variable's value. The two variable sets are not interchangeable: a plain format names the composed values, and the cell's format names the composed variable. A declaration may also carry `shownUntil`, the reading that says when a timed datum stops showing: binding resolves the text and then hands it to the timed visual in `components/visuals/` with the render's `sampledAt`, and nothing to show renders as nothing, so the cell drops its label and gap. The bound `(readings, width, theme) => string` renders its format with those values. A format may carry `|name` modifiers after a variable or after the text in front of them, and the language commits to one order: of the names, a form the variable declares, then one of Jefferson's own, then a foreground colour the live theme carries; and of the work, it renders the cell empty when a variable the format names is unknown, collapses control characters, trims a format's outer whitespace when it parses, runs a segment's string mutations in the order the format writes them, measures the columns `$bar` leaves, and styles each segment once, in the first colour that applies — the last colour its chain names, else the variable's declared token, else the `style`'s `fg`. A declared variable the format does not name is never resolved, so it cannot blank the cell; see [ADR 0020](docs/adr/0020-only-a-variable-the-format-names-can-blank-an-instrument.md). It also says whether it fills the row's spare columns, which is how a row sizes its cell. Instruments know nothing about alignment.

**Visuals.** `components/visuals/` holds the parts an instrument can mix in, each in its own file and importing no file of this package, so a change to the format language or to an instrument cannot reach one. The bar draws a filled track: `format.ts` parses `$bar` and gives it the columns the row left, and `bar.ts` draws it.

The timed visual decides whether a timed datum shows. It compares the instant the datum shows until against the render's instant. Before that instant the text comes back unchanged; at or after it, or when either instant is missing, it hands back nothing, and the cell renders nothing, label included. The binding applies it after the format resolves, for a declaration that declares `shownUntil`.

**Row renderer.** Builds one `VStack` at install, retaining every cell component. Its children are one `HStack` per row and nothing else, and its `gap` is the configuration's `rowGap`. The stack puts `gap` empty lines between its children, so row one sits flush on the editor; see [ADR 0008](docs/adr/0008-the-space-between-rows-is-the-stacks-gap.md). `rowGap` reaches the renderer once, at install. The vertical gap is that `gap`; the horizontal one below is the `HStack`'s. On each render the renderer asks every cell for the width of its text at width 0 and gives those to the width plan in `components/row/`, a pure function that returns each cell's basis, grow and joint. `blank` and `$bar` cells fill. The joint is one column owned by the right-hand cell, drawn as a leading space inside it. Every cell is `shrink: 1` with `minSize: 0`, so a row over its width loses columns to the host's allocator and stays one line; the allocator also spends any remainder (the `HStack`'s `gap: 0`). A row with `distribution: "equal"` skips the probe: every cell gets `floor(W / N)` and `grow: 1`, as [ADR 0002](docs/adr/0002-rows-span-the-full-width.md) recorded. No configuration reaches that path now: the parser writes `"content"` for every row, and [ADR 0016](docs/adr/0016-the-equal-distribution-stays-in-the-code.md) keeps the branch for the code. The same components are re-seated with `clear()` plus `addChild` when the width changes or any plan field the cells read does: the basis, the grow or the joint. Every cell reads the current render's sample from the footer's slot, and its memo holds one text per width per sample, so a repeated render of the same sample resolves nothing new; invalidation clears the memo. Each cell clips with `truncateToWidth`, pads with `visibleWidth`, and returns one line; composition and allocation stay with the host. The choice and what it weighed are in [ADR 0007](docs/adr/0007-a-cell-takes-the-width-its-content-needs.md).

## Import direction

One way only, and no cycles. The entry imports startup and nothing else. Startup imports what it installs. No file imports the entry. Within `extensions/jefferson/`:

- `data/` holds the files that keep session data, the fields a provider declared, and the view those fields are read through. It imports host packages and its own files, and no file outside `data/`. `data/provider-fields.ts` imports only `data/field-value.ts`.
- `instrument-contract.ts` imports only the types of `data/field-value.ts`, and it holds no runtime statement.
- `faults.ts` imports no file of this package.
- `registration.ts` imports the type `components/instruments/instrument.ts` declares.
- `registration-listener.ts` imports `registration.ts`, the types of `faults.ts`, the contract, the types of `data/`, the `instrument.ts` type, the foreground check `format.ts` exports, and the binding.
- `components/` holds the parts. Its files import host packages, their own directory, a visual, the types of `data/` and `format.ts`. They never import startup, footer setup, configuration or `shipped.ts`.
  - `row/` imports only the `Instrument` type from `components/instruments/instrument.ts`.
  - `instruments/` imports `format.ts` and a visual only in the binding, and the binding imports the `Fault` type from `faults.ts`. Its files may import the contract's types, and `instrument.ts` and the binding both do.
  - `components/visuals/` files import no local file.
- `format.ts` imports `components/visuals/bar.ts` and the types of `components/instruments/` and `data/`.
- `shipped.ts` imports the instrument files.
- Everything above those directories may import any of their files.

Host packages (`@earendil-works/*`) are `peerDependencies` with a `*` range and never `dependencies`. Any shipped file may import one; see `docs/adr/0001-imports-run-one-way.md` for why the older entry-only rule was retired.

The package's one runtime dependency, `lodash-es`, supplies a format modifier's string mutations; see [ADR 0004](docs/adr/0004-string-mutations-come-from-lodash-es.md). A format's styling needs no dependency: its modifiers are pi's own six attributes and the live theme's own foreground names.

## Two things that will bite

**A pad needs a reset.** Cell text may carry ANSI styling. A pad that follows text which left an SGR open inherits that styling — underline painting trailing spaces, or a background bleeding across a cell. The renderer emits a reset before such a pad. The host resets between children, so crossing a cell boundary is already handled; the intra-cell case is ours. The pad itself splits three ways on the cell's `align` — after the text for `left`, before it for `right`, halved around it for `center` — and the `leavesStyleOpen` rule guards only the pad that follows the cell's own text.

**Widths are columns, not characters.** Always measure with `visibleWidth` and clip with `truncateToWidth`. `String.length` is wrong for emoji, CJK, combining marks and ANSI escapes, and a wide glyph dropped at a clip boundary leaves the text narrower than arithmetic predicts, so a pad must be computed from the clipped result.

## Fidelity

Rows span the full width. The leftover columns go to the fill cells, split evenly with the odd columns to the earliest; with no fill cell, to the last left-aligned non-empty cell, else the first non-empty cell, else the first cell. Under `distribution: "equal"` they go to the earliest cells, one each — a path no configuration selects now, since the parser writes `"content"` for every row ([ADR 0016](docs/adr/0016-the-equal-distribution-stays-in-the-code.md)). A right-aligned last cell ends at the window's edge. This replaces the former blank-right-edge property, recorded in [ADR 0002](docs/adr/0002-rows-span-the-full-width.md); the content-sized default is [ADR 0007](docs/adr/0007-a-cell-takes-the-width-its-content-needs.md).

## Tests

`node --test`, source executed directly with type stripping — erasable TypeScript only, no build step. Tests live under `tests/` and never beside a source file. pi loads only the entry the `pi.extensions` manifest in `package.json` names, `extensions/jefferson.ts`, but `files` ships all of `extensions/`, so a test file beside a source file would ship in the package. The renderer's expectations state the host's per-child framing once, in a helper, and assert visible text where the framing is not the subject.
